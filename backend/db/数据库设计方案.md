# 校友管理平台数据库设计（v3）

> 版本：v3.0　日期：2026-09-17　依据：《[定稿]API规范》v1.2 十二章
> 地位：**全平台唯一结构基准**，配套脚本 [schema.sql](schema.sql)（全量 DDL，MySQL 8.4 实测通过）
> 纪律：模块目录禁止再建 DDL 文件；改表 = 改 schema.sql + 增量迁移脚本（幂等守卫）→ 评审 → 灰度 → 生产
> 本文替代 v2 版方案（v2 差异对照与模块迁移指引见 §7）

---

## 1. 总览与约定

| 项 | 约定 |
|---|---|
| 库 | 单库 `alumni_platform`，utf8mb4 / InnoDB / `utf8mb4_unicode_ci` |
| 规模 | 15 张表、19 个外键（Stats 不建表，纯聚合查询） |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT` |
| 时间 | 全 UTC `TIMESTAMP(6)`；连接串 `serverTimezone=UTC`，会话 `SET time_zone='+00:00'`；出参 ISO 8601 |
| 枚举 | VARCHAR + 应用层校验（不用 ENUM，改值免 ALTER） |
| 删除 | 外键默认 RESTRICT；业务删除走逻辑状态 / 审核流，保审计链路 |
| 验证码类 | 短信码 / verify_token / reset_token 存 **Redis**（限时一次性），不落库 |

## 3. 表清单（15 表）

| 模块 | 表 | 用途 | 关键约束 / 索引 |
|---|---|---|---|
| Auth | `alumni_base` | 校友库（三要素核验数据源） | `uk(student_id)`；`idx(college, grad_year)`、`idx(real_name)` |
| Auth | `users` | 平台账号 | `uk(uuid)`、`uk(student_id)`、`uk(phone)`、`uk(alumni_base_id)` |
| Auth | `refresh_tokens` | 刷新令牌 | `uk(token_hash)`，存 SHA-256 散列不落明文 |
| Dicts | `dicts` | 基础字典（层级：major 归属 college，`parent_id` 自引用） | `uk(type, value)`；`idx(type, sort)`、`idx(parent_id)` |
| Attachments | `attachments` | 附件（跨模块复用） | `idx(biz_type, ref_id)`；`idx(status, created_at)` 供孤儿清理 |
| Attachments | `attachment_audit_log` | 删除审计 | 只增不删，保留 ≥180 天 |
| Archives | `archives` | 校友档案 | `idx(user_id)`、`idx(status, category)` |
| Honors | `honors` | 校友荣誉（统计唯一数据源） | `idx(category, level)` 供分布统计 |
| Reviews | `reviews` | 审核记录（独立资源） | `idx(biz_type, stage, status)` 待办高频查询 |
| Reviews | `review_logs` | 审核日志 | `idx(review_id)` |
| Consents | `consents` | 隐私授权 | `uk(archive_id, scope)` |
| Showcase | `showcase` | 上架记录 | `uk(archive_id)`；行存在 = 上架中 |
| Drafts | `drafts` | 草稿（服务端兜底） | `uk(user_id, biz_type)`；version 乐观锁 |
| Imports | `import_tasks` | 导入任务 | 异步：processing → done |
| Imports | `import_errors` | 错误行报告 | `idx(import_id)` |

## 4. 核心设计决策

1. **人的锚点 + 对外 UUID 分离**：内部关联一律 `users.id`（自增、JOIN 快）；对外平台对接用 `users.uuid`（v4 随机、创建即生成、不可变），库重建 ID 重排也不影响外部映射。
2. **校友库独立成表**：`alumni_base` 是权威数据源（激活核验、批量导入目标），`users` 仅存激活后的账号，二者 1:1（`uk(alumni_base_id)`）。身份证号明文存于 `alumni_base.id_card`（决策人拍板，仅核验用、出参必脱敏；生产建议 TDE + 库级权限隔离）。
3. **两条多态总线**：附件 `(biz_type, ref_id)`、审核 `(biz_type, biz_id)` 不加外键——新模块接入零改表；引用完整性由应用层保证，`ref_id IS NOT NULL` 即"已引用"。
4. **档案版本用单行计数**：驳回重提 `version+1` 不复制行，历史轨迹落在 `review_logs` 审计中，`/archives/my` 查询无需"取最新版本"的窗口函数。
5. **荣誉独立结构化**：honors 不是 archives 的 category（规范明示），统计接口只扫本表；同样有审核状态字段（走 Reviews 通道）。
6. **上架/授权的存在即状态**：`showcase` 行存在=上架中（发布时快照封面 `cover_attachment_id`）；`consents` `(archive_id, scope)` 唯一，撤回=删行并联动下架。大屏 feed = showcase ⋈ archives(approved) ⋈ consents，未授权内容绝不上屏（越权红线）。
7. **字典层级化 + 虚拟类型**：`dicts.parent_id` 自引用——major 必须归属 college（创建强制校验），其余类型平级；删除父级前必须先移除子项（409），业务引用（alumni_base 文本对齐 / honors.category）同样拦截删除与改值。`grad_year` 为**虚拟类型不落库**——年份是可枚举数据而非业务主数据，接口按当前年动态生成（-20 ~ +4，可配），该类型禁止增删改。
8. **Stats 零存储**：overview / honors / colleges 全部实时聚合（`COUNT(users)`、`reviews pending`、`GROUP BY honors(category,level)`、`GROUP BY alumni_base.college`），十万行内毫秒级；量级上来后优先加只读从库，不加冗余表。

## 5. 索引策略

按查询路径建索引，不为"可能用到"建索引；写多的日志/审计表控制索引数量：

| 高频查询 | 命中索引 |
|---|---|
| 登录 / 激活核验 | `users.uk_phone`、`alumni_base.uk_student_id` |
| 待办列表（学院 first / 校级 second） | `reviews.idx(biz_type, stage, status)` |
| 我的档案 / 驳回回显 | `archives.idx(user_id)` + 行内 `reject_reason` |
| 荣誉分布统计 | `honors.idx(category, level)` |
| 学院排行 | `archives ⋈ users ⋈ alumni_base`，`idx_alumni_base_college_year` |
| 孤儿附件定时清理 | `attachments.idx(status, created_at)` |
| 大屏 feed | `showcase.uk(archive_id)` + `consents.uk(archive_id, scope)` |

不建 FULLTEXT：档案关键词仅"学号/姓名"（走 users / alumni_base 索引）；未来全文检索引 Elasticsearch，不用 MySQL FULLTEXT。

## 6. 安全与运维规则

| 资产 | 措施 |
|---|---|
| 密码 | 前端 SHA-256 → 服务端 BCrypt 入库（规范 1.7），库中无可逆形式 |
| refresh_token | 只存 SHA-256 散列；轮换制，登出/改密整户作废 |
| 身份证号 | 明文存 `alumni_base.id_card`（仅核验）；出参一律脱敏；生产开 TDE + 独立库级权限 |
| 手机号 | 出参脱敏 `138****1234`；`uk(phone)` 防重复绑定 |
| 审计 | `attachment_audit_log` 只增不删 ≥180 天，建议按月归档；`review_logs` 记录全部审核动作 |
| 数据库账号 | 生产禁用 root：应用账号仅授 `SELECT/INSERT/UPDATE`（不授 DELETE/DROP/ALTER），迁移用独立运维账号 |
| 备份 | 生产每日全量 + binlog 增量；迁移/改表前必须 `mysqldump` 备份 |

## 7. v2 → v3 差异对照（模块迁移指引）

> v2 方案（`alumni` 库）作废，以下差异各模块负责人按行对齐：

| 差异点 | v2（旧） | v3（现行） | 影响 |
|---|---|---|---|
| 库名 | `alumni` | `alumni_platform` | 连接配置改库名 |
| 用户模型 | users 单表（含 real_name / college_id / status / id_card_enc） | `alumni_base` + `users` 两表 1:1，新增 `uuid` | **stats 模块**：学院排行 JOIN 改为 `archives ⋈ users ⋈ alumni_base GROUP BY alumni_base.college`；用户计数不变 |
| 身份证 | `id_card_enc` AES-256-GCM | `alumni_base.id_card` 明文（决策已定） | 加密代码可移除 |
| 短信验证码 | `sms_codes` 表 | **Redis**（auth 已落地） | 勿再建表 |
| 人工核验申请 | `activate_manual_requests` 表 | 本期不实现（规范 2.1.4 缓建） | — |
| 附件关联列 | `biz_id` | `ref_id` | 附件模块按 `ref_id` 开发 |
| 字典表 | `dicts` | `dicts`（同名保留，含 updated_at） | 无影响 |
| 审核表 | `reviews(+submitter_id)` / `review_logs(operator_id, action=create/approve/reject)` | **同名同结构已对齐** | **reviews 模块：零改动** |
| 档案版本 | `root_id + version` 版本链（多行） | 单行 `version` 计数 | archives 模块按单行模型开发 |
| 授权/上架 | `revoked_at` / `unpublished_at` 软删 | 删行 + 行存在即状态 | consents/showcase 按新模型开发 |
| 导入任务表 | `imports` | `import_tasks` | imports 模块改名即可 |
| 草稿载荷 | TEXT | JSON | drafts 模块用 JSON 列 |

## 8. 演进方向

- 数据量 >50 万行：统计查询迁只读从库；`review_logs` / `attachment_audit_log` 按月分区归档
- 全文检索：档案 title/content 接 Elasticsearch，库结构不变
- 主键平滑切雪花 ID：应用层生成，库结构不变（对外已是 UUID，无暴露风险）
