# 荣誉大屏后台重构 · 测试报告与用户操作手册

> 文档版本: 2026-10-01
> 涉及模块: honors (后端) + admin (前端) + portal (前端)
> 关联 Flyway 迁移: **V17__honor_screen_online.sql**
> 任务编号: **[P1/M17]**

---

## 1. 改造背景

`honors.status` 字段语义是**审核态**(pending_counselor/.../approved/rejected),
与**"是否在前台大屏展示"**并不等价。一个荣誉可能审核被驳回但仍需在大屏归档展示,
反之审核通过的荣誉也可能临时下架维护。

原方案没有任何上下架控制,后台也无法只让部分数据进入前台大屏,
导致生产中常出现"测试数据上屏"、"敏感荣誉无法下架"等问题。

本次重构**新增独立字段 `screen_status`**,与审核 `status` 完全解耦,
同时引入完整审计日志,确保所有变更可追溯。

## 3. 数据库变更 (Flyway V17)

### 3.1 新增列

```sql
ALTER TABLE honors
    ADD COLUMN screen_status VARCHAR(16) NOT NULL DEFAULT 'offline';
CREATE INDEX idx_honors_screen_status ON honors (screen_status);
```

- 老数据默认填充 `offline`(保守策略:不自动上屏,避免老内容误展示)
- 取值:`online` 可见 / `offline` 不可见
- 独立索引保证 `WHERE screen_status = 'online'` 高效

### 3.2 新增表 honor_screen_log

| 列 | 类型 | 含义 |
|---|---|---|
| id | BIGINT PK | 主键 |
| honor_id | BIGINT NOT NULL | 关联荣誉 ID |
| action | VARCHAR(16) | online / offline / batch_online / batch_offline |
| before_status | VARCHAR(16) | 变更前 |
| after_status | VARCHAR(16) | 变更后 |
| reason | VARCHAR(500) | 操作原因(可空) |
| operator_id | BIGINT | 操作人 users.id |
| operator_name | VARCHAR(64) | 操作人姓名(冗余) |
| operator_role | VARCHAR(32) | 操作人角色 |
| client_ip | VARCHAR(64) | X-Forwarded-For 优先 |
| batch_size | INT | 批量操作时的请求总数(单条为 1) |
| request_id | VARCHAR(64) | 关联 RequestId |
| created_at | DATETIME(6) | 变更时间 |

3 个二级索引(honor_id / action / operator_id / created_at),保证审计查询性能。

## 4. 后端接口

### 4.1 新增接口

| Method | Path | 说明 |
|---|---|---|
| POST | `/api/v1/admin/honors/{id}/screen-status` | 单条上下架 |
| POST | `/api/v1/admin/honors/screen-status:batch` | 批量上下架(≤500 条) |
| GET  | `/api/v1/admin/honors/screen-logs` | 上下架变更日志(分页) |

#### 4.1.1 单条上下架

```http
POST /api/v1/admin/honors/87/screen-status
Authorization: Bearer <token>
Content-Type: application/json

{ "status": "online", "reason": "测试上架" }
```

响应:
```json
{
  "code": "OK",
  "data": {
    "requested": 1,
    "applied": 1,
    "skipped": 0,
    "failed": 0,
    "failures": []
  }
}
```

- `applied=0, skipped=1`: 已是目标态(无变更,但日志仍写入一条审计)
- `failed>0`: 仅 college_admin 跨院操作时返回 `failures[]`

#### 4.1.2 批量上下架

```http
POST /api/v1/admin/honors/screen-status:batch
Authorization: Bearer <token>
Content-Type: application/json

{
  "ids": [87, 88, 999999],
  "status": "online",
  "reason": "国庆展示"
}
```

响应 `failures[]` 包含不存在/越权的 id。

#### 4.1.3 日志分页

```http
GET /api/v1/admin/honors/screen-logs?honor_id=87&action=online&page=1&page_size=20
Authorization: Bearer <token>
```

支持筛选:`honor_id`、`action`、`operator_role`、`page`、`page_size`。
college_admin 仅可见本院操作日志(通过 `operator_role=college_admin` 兜底)。

### 4.2 既有接口增量

| Method | Path | 新增参数 |
|---|---|---|
| GET | `/api/v1/admin/honors` | `screen_status` (online / offline) |
| GET | `/api/v1/admin/honors/export` | `screen_status` |

### 4.3 前台接口(自动应用,无需前端改)

`/api/v1/dashboard-honor` 返回的所有聚合数据(KPI / 类型分布 / 学院 Top /
届别分布 / 荣誉榜单 / 校友 Top)均已加 `AND screen_status = 'online'` 过滤。
portal 大屏 `HonorScreen.vue` 的 30 秒自动刷新机制确保**实时同步**。

## 8. 用户操作手册

### 8.1 上下架单条荣誉

1. 登录管理端(校级/院系/系统管理员)
2. 进入「荣誉管理」页
3. 在目标荣誉「操作」列点「上架」或「下架」
4. 弹出确认框,输入/确认原因(可空),点「上架/下架」
5. 系统提示「上架成功」并刷新列表;该荣誉「操作」列自动切换为对偶按钮

### 8.2 批量上下架

1. 进入「荣誉管理」页
2. 勾选多条记录(顶部出现「已选 N 条」蓝色提示条)
3. 在工具栏点「批量上架」或「批量下架」
4. 弹出确认框,确认原因,点确定
5. 系统返回成功条数 / 已为目标态 / 失败原因,
   例如: "请求 3 条;已变更 2;已是目标态 0;失败 1"

### 8.3 筛选特定状态

- 「大屏状态」下拉:已上架 / 已下架(与「状态」并列,可同时组合筛选)
- 「类别 / 学院 / 届别 / 级别 / 关键词」与其他筛选维度可组合

### 8.4 查看上下架日志

1. 表头右上「上下架日志」按钮
2. 弹出对话框,默认按时间倒序
3. 字段:日志ID / 时间 / 荣誉ID / 荣誉名称 / 操作(单条/批量 上/下架) /
   变更(已下架 → 已上架)/ 操作人(角色)/ IP / 批量数 / 原因
4. 翻页查看历史变更;可联系审计人员定向追溯

### 8.5 前台大屏验证

- 校级/院系管理员勾选「上架」后,**最多 30 秒** portal 大屏自动刷新
- 校验路径: `http://localhost:5175/dashboard` 看荣誉榜单是否出现
- 紧急下架同样 30 秒内生效;刷新频率在 admin 端「屏幕配置」可调(0=手动刷新)
